# CLAUDE.md — правила Claude Code-станка (нативная память)

## Миссия
Ты — модель на Claude Code-станке. Выполняешь задачи из тикета `TASK-STANOK-CC-NNN`
(тикет приходит текстом в промпте). Тикет самодостаточен: не ищи спеку в других
каталогах — всё нужное уже в тикете. `tickets/` — только чтение.

## Жёсткие правила (нарушение = провал задачи)
1. Пиши ТОЛЬКО в каталоги `src/`, `tests/`, `docs/`. Всё остальное (CLAUDE.md, .claude/,
   hooks/, .git/, evidence/, tickets/, корень репо) — protected: запись туда
   будет заблокирована.
2. Используй ТОЛЬКО инструменты: **Read, Write, Edit, Grep, Glob, WebFetch** +
   **Agent для под-агентов `reviewer`** (независимая проверка, шаги 5-7) **и `tester`**
   (создание/правка тестов). Bash/exec/WebSearch нет. Прочие субагенты недоступны —
   не пытайся их вызывать. **После первого прогона verifier тест залочен
   (`.stanok-locks/`): править `tests/*.test.js` имеет право ТОЛЬКО `tester`-субагент;
   main-агент (coder) залоченный тест не трогает — попытка будет заблокирована
   (test-lock deny).** **WebFetch доступен ТОЛЬКО для разрешённых read-only доменов:
   `arxiv.org`, `github.com`, `docs.anthropic.com`, `code.claude.com`,
   `developer.mozilla.org`, `nodejs.org`, `docs.python.org`, `npmjs.com`, `pypi.org`**
   (только https, точное совпадение домена; префикс `www.` допускается как тот же сайт;
   subdomain-обходы вроде `raw.githubusercontent.com` НЕ разрешены). Любой другой домен
   через WebFetch идёт на ручной гейт оператора (Telegram, таймаут -> DENY) — не
   пытайся. Запись вне `src/tests/docs` автоматически идёт на ручной гейт оператора
   (Telegram, таймаут -> DENY) — не пытайся обойти; заблокированное действие вернёт deny.
3. НЕ коммить, НЕ трогай .git.
4. НЕ меняй конфигурацию станка (.claude/settings.stanok.json, hooks/, CLAUDE.md).
5. Создавай только то, что просит тикет. Без лишних файлов.
6. Не выходи за пределы этого репозитория (запись — только внутрь src/tests/docs).

## Целевая структура задачи
- `src/<module>.js` — реализация функции
- `tests/<module>.test.js` — тесты функции
- `docs/<module>.md` — краткая документация

## Порядок работы
1. Прочитай текст тикета.
2. Ознакомься с существующей структурой (Grep/Glob/Read). cwd — корень репо:
   относительные пути БЕЗ префикса (`src/*.js`, `tickets/*.md`), не `stanok/...`.
   НЕ используй `**/*` по корню — список обрезается до 100 файлов и `.git/objects/*`
   вытесняет из видимости `src/` и `evidence/` (это читается как «дерево стёрто» —
   не делай таких выводов). Используй точечные паттерны: `src/**`, `tests/**`,
   `tickets/*.md`, `evidence/<label>/*`.
3. Напиши тест ПЕРВЫМ (TDD): тест должен сначала упасть — красная фаза
   (VERIFY: FAIL, модуль ещё не существует). Затем реализуй функцию, пока тест не
   пройдёт — зелёная фаза (VERIFY: PASS). Затем документацию. Не наоборот.
4. Проверь (Read), что всё создано корректно.
5. **Вызови Agent (`subagent_type: "reviewer"`) для независимой проверки**
   созданных/изменённых файлов в `src/` и `tests/`. Это обязательный шаг каждого тикета.
6. Если вердикт `REVIEW-VERDICT: DEFECT <file> <line>: <что не так>; <фикс>` —
   исправь указанный дефект и снова вызови reviewer. Повторяй, пока не получишь
   `REVIEW-VERDICT: CLEAN`.
7. После `REVIEW-VERDICT: CLEAN` — в отчёте укажи, что файлы прошли независимый review.

## Механический верификатор (вне модели, детерминированный)
- Сзади тебя работает независимый гейт: после каждого Write/Edit — `hooks/verifier.sh`
  (PostToolUse), а лаунчер прогоняет ВСЕ `tests/*.test.js` (`node`, реальный exit код).
  Итог — `VERIFY: PASS` / `VERIFIER: FAIL` + rc лаунчера.
- **Граница верификатора:** гейт проверяет «код ↔ тест» — модуль против своего теста, а НЕ
  «тест ↔ смысл тикета». Верно ли понят тикет — твоя ответственность; гейт лишь
  гарантирует: если тест падает — прогон не успешен.
- Гейт вне модели: он не зависит от твоего текста и не читает твои ответы. FALSE-CLEAN
  (reviewer сказал CLEAN, тест падает) ловится механически, «заболтать» его нельзя —
  потребитель вердикта — внешний раннер, а не цитата модели.

## Малвар-скан: механический флаг -> эскалация через reviewer
- После каждого Write/Edit в `src/` хук `hooks/malware-scan.sh` (PostToolUse) сканит
  написанный код на подозрительные паттерны (`child_process`, `net`, `eval(`,
  `new Function(`, `exec(/execSync(`, `spawn/fork(`, `process.env`, base64-декод) и при
  находке пишет evidence-строку `FLAGGED-FOR-REVIEW` + pending-флаг. Это НЕ блокировка:
  код проходит, только флаг.
- Если в контексте появилось сообщение `MALWARE-SCAN: FLAGGED-FOR-REVIEW file=<path>
  patterns: <...>` (приходит как системное напоминание после Write) — ты ОБЯЗАН спавнить
  существующего reviewer (`Agent`, `subagent_type: "reviewer"`) и передать ему эту метку
  вместе с контекстом тикета для вердикта по секции «Security check». Это отдельная
  обязанность поверх обязательного шага 5.
- Если вердикт `REVIEW-VERDICT: DEFECT` по security-причине — убрать/объяснить паттерн
  и снова вызвать reviewer, пока не `REVIEW-VERDICT: CLEAN`. НИКОГДА не оставляй
  необъяснённый подозрительный паттерн в коде.
- Внешний раннер следит за `pending-*.flag`: пока флаг висит без вердикта reviewer
  `CLEAN` — rc принудительно ненулевой (`SECURITY-PENDING`). Вердикт принимается из
  вывода субагента, а не из твоего текста, — «заболтать» нельзя.

## Отчёт
Финальный отчёт — СТРОГО ≤ 10 строк. Формат:
1. `TASK-STANOK-CC-NNN: DONE`
2. Созданные/изменённые файлы (по одному на строку)
3. `VERIFY: PASS` / `VERIFIER: FAIL` + rc
4. `REVIEW-VERDICT: CLEAN` / `SECURITY-PENDING`
Никакого recap, объяснений, markdown-заголовков, списков с подпунктами.
