## Находки

### A-1. Алиасинг строк доски после очистки ≥2 рядов — MEDIUM

**Утверждение.** `_lock_and_clear` создаёт новые пустые ряды выражением
`[[0] * width] * cleared` (E:116) — при `cleared >= 2` это **один и тот же
list-объект**, повторённый в нескольких строках доски. Состояние содержит
самоссылающуюся доску: изменение одной строки создаёт фантомные клетки в другой.

**Доказательство (зонд 2).** Fixture: rows 18–19 заполнены кроме cols 0–1, O
локится → `cleared = 2`:

```
out.board[0] is out.board[1] -> True
after out.board[0][5]=9: out.board[1][5] = 9      # мутация одной строки
try_move(out, +1) -> None — заблокировано фантомом (1,5), порождённым мутацией алиасированной строки board[0]
```

Дефект присутствует в состоянии, которое порождает **собственный тест**
`T-engine::test_score_tetris_four_lines` (fixture из теста, `cleared = 4`):

```
board[0] is board[1] -> True
board[0] is board[3] -> True
after board[0][0]=9 -> board[3][0]: 9
```

**Почему тесты пропускают.** Ни один тест не очищает 2–3 ряда (в T-engine есть
только очистка 1 ряда — `T-engine:161` — и 4 ряда — `T-engine:191`), а тест 4-ряда
проверяет только score/lines_cleared (значения), но не идентичность строк.
Внутри движка дефект невидим: каждая операция перед записью копирует строки
(`[row[:] for row in state.board]`, E:104), поэтому игровая логика не ломается —
ломается модель «State — независимый снимок».

### A-2. Нелocking-операции возвращают состояние, разделяющее board с входом — MEDIUM

**Утверждение.** `try_move` (E:143), `try_rotate` (E:153) и падающие ветки
`_fall_or_lock` (E:125) делают `dataclasses.replace(state, ...)`, который
копирует поля **по ссылке**: `result.board is input.board` → True. Два «снимка»
—one вход, один выход — это один и тот же board. Мутация выходного состояния
задним числом меняет входное.

**Доказательство (зонд 2).**

```
try_move: result.board is input.board -> True
tick (no lock): result.board is input.board -> True
after moved.board[0][0]=9: input st.board[0][0] = 9   # мутация результата меняет «исходный снимок»
hard_drop (lock): result.board is input.board -> False # lock копирует — только он
```

**Почему тесты пропускают.** `T-engine::test_functions_do_not_mutate_input_state`
проверяет, что *движок* не мутирует вход (значения до/после), но не проверяет
разделение объектов между входным и выходным состояниями. Пока никто не мутирует
board извне, алиасинг невидим; для любого следующего тикета с историей/реплеем/
снапшотами состояний (сравнить два состояния, откатить) это ловушка.

### A-3. «Frozen» State неизменяем лишь наполовину — MEDIUM

**Утверждение.** `@dataclass(frozen=True)` (E:50) с полем `board: list` (E:55)
блокирует только переприсваивание атрибутов. Клетки доски мутируемы извне, и это
меняет поведение движка: фантомные клетки, изменённая посадка фигуры, «запрещённые»
ид на доске.

**Доказательство (зонд 2).**

```
st.board[19][4] = 5 accepted (frozen only blocks attribute rebinding)
st.x = 7 rejected: FrozenInstanceError
active piece id=2: after hard_drop its cells sit above the floor at (17,4)  # посадка на фантом
phantom cell still on board: dropped.board[19][4] = 5
board non-zero cells after two hard_drops with phantom: 9  # id=4 пережил игру как «запертая» клетка фигуры, которой не было
```

**Почему тесты пропускают.** Контракт `docs/tetris_engine.md` обещает «input
State is never mutated» — движок это соблюдает (см. «Проверено», П-2), и тесты
проверяют именно это. Никто не проверяет обратное: что состояние *защищено от
внешней мутации*. `frozen=True` создаёт ложное ощущение неизменяемости; в
сочетании с A-1/A-2 это один корень: доска — разделяемый мутабельный список.

### A-4. Интерактивный режим игнорирует EOF: процесс не завершается никогда — MEDIUM

**Утверждение.** Контракт `docs/tetris_cli.md`: цикл «until q/SIGINT». EOF без
`q` — не `q`: интерактивный цикл (C:254–280, условие `while max_frames is None`,
C:268) продолжает работать бесконечно, рендеря кадры. Конфликт с естественным
контрактом CLI (поток ввода исчерпан → завершиться), которого bounded-mode
избавлен.

**Доказательство (зонд 3, внешний `timeout 10`).**

```
python3 -m src.tetris_cli --width 6 --height 4 </dev/null   -> rc=124 (timeout), ~23 кадра за 10 с (28926 байт)
printf 'a\nd\n' | python3 -m src.tetris_cli --width 6 --height 4 -> rc=124   # EOF проигнорирован
printf 'a\nd\nq\n' | ...                                      -> rc_q=0      # q работает
SIGINT -> rc=0                                               # SIGINT работает
```

**Почему тесты пропускают.** T-cli никогда не запускает интерактивный цикл без
тестового крючка `max_frames` (`T-cli:165–179`); subprocess-тесты используют
только `--ticks`. Бесконечный цикл без крючка не тестируется в принципе.
По ticket-конракту это **не успех и не исправляется** — это нерешённый вопрос:
либо EOF должен быть штатным условием выхода, либо контракт должен явно
предписывать вечную работу до q/SIGINT.

### A-5. Цветовой шов CLI→рендерер нигде не тестируется — MEDIUM (пробел тестов с регрессионным риском)

**Утверждение.** `_render_frame` (C:216–222) конвертирует 0/1-матрицу движка в
оверлей с `piece_id`. Если бы эта конвертация пропала (оверлей = `state.piece`
как есть), **все фигуры рендерились бы cyan** (cells=1 → `PIECE_COLORS[1]`), и все
11 CLI-тестов остались бы зелёными: они проверяют лишь наличие `FG_PREFIX` и
`GLYPH` (`T-cli:113–114`, `T-cli:190`), но не цвета.

**Доказательство.** Grep по `tests/tetris_cli_test.py`: `PIECE_COLORS`,
`_render_frame`, `_apply` — ни одного вхождения. Сквозной зонд 1 подтвердил, что
*сейчас* шов корректен (см. П-1), но защитного теста нет.

**Почему тесты пропускают.** T-render тестирует маппинг id→цвет на своих
собственных матрицах; T-engine тестирует board-значения; стык (движок хранит
0/1 + отдельный piece_id, рендерер красит по значению ячейки) не покрыт ничем.

### A-6. Валидация рендерера обещана документом, но не тестируется — MEDIUM (пробел тестов)

**Утверждение.** `docs/tetris_render.md` обещает `ValueError` для: рваных строк
(«ragged rows»), значения клетки вне `0/1..7`, и некорректного цвета в
`render_cell`. Реализация есть (R:77–79, R:49–52, R:34–41), тестов нет.

**Доказательство.** Grep по `tests/tetris_render_test.py`: единственный
валидационный тест — `test_odd_height_raises_value_error` (рост высоты).
Ни одного теста на `len(row) != width`, на board-значение `8`/`-1`, на
`render_cell((10,20,300), ...)`.

**Почему тесты пропускают.** Валидационные ветки просто не вызываются ни одним
тестом; их регрессия (например, «тихо дорисовать» вместо raise) не будет
замечена.

### A-7. Узкие доски: CLI принимает width 1..3, где игра заканчивается на спавне — LOW

**Утверждение.** `--width` валидируется только как `>= 1` (C:80). Формула спавна
`x = (width - matrix_width) // 2` (E:94) при узкой доске даёт отрицательный x →
спавн-коллизия → немедленный game over (E:96–98).

**Доказательство (зонд 4 + CLI).**

```
seed=14 first piece=I on width 3: spawn x=-1, game_over immediately = True
width 1: new_game(1,1,2).game_over = True   # любая фигура шире 1 колонки
width 2: seed 1 (O) выживает, но любая 3-широкая фигура (T/S/Z/J/L) даёт x=-1 -> game over
CLI: --width 1 --height 2 --ticks 1 -> rc=0; --width 3 --seed 14 -> rc=0 (игра мертва с первого кадра)
```

**Почему тесты пропускают.** Формула спавна и game-over на спавне тестировались
только на досках ширины 10. Формально поведение соответствует документу
(«spawn collision is the only game-over condition») — дефекта нет, есть
необъявленная вырожденная зона CLI-валидации.

### A-8. Состояние game-over сохраняет активную фигуру, и CLI рисует её поверх доски — LOW (косметика)

**Утверждение.** `_spawn` при коллизии всё равно устанавливает
`piece_id/piece/x/y` и лишь затем `game_over=True` (E:96–99). `_render_frame`
рендерит оверлей и на game-over-состоянии (C:218 проверяет только `piece == ()`).

**Доказательство (зонд 4d).**

```
hard_drop -> game_over=True
game-over state still carries an active piece: piece_id=5, piece set=True
```

В финальном кадре «мёртвой» игры фигура перекрывает стопку. Тесты пропускают:
`T-engine::test_game_over_on_blocked_spawn` проверяет флаги, но не состав
состояния после game-over-спавна и не кадр.

### A-9. Неполная строка из открытого канала блокирует ввод — LOW

**Утверждение.** `_drain_lines`: `select(...,0.0)` говорит «данные есть», затем
`stdin.readline()` **блокируется до перевода строки или EOF** (C:120–121).
Писатель, держащий канал открытым и пишущий без `\n`, останавливает игровой цикл
— даже детерминированный bounded-режим, который документ называет не блокирующимся
(«never blocks on absent input» — формально верно: блокирует не при *отсутствии*,
а при *неполном* вводе).

**Доказательство (зонд 5).**

```
(printf 'a'; sleep 30) | timeout 5 python3 -m src.tetris_cli ... --ticks 1 -> rc=124  # висит в readline
printf 'a\n'            | timeout 5 python3 -m src.tetris_cli ... --ticks 1 -> rc=0
```

**Почему тесты пропускают.** T-cli всегда закрывает stdin (subprocess input=…,
io.StringIO) — неполной строки при открытом канале не бывает.

### A-10. `_piece_at` перебирает RNG-поток заново на каждый спавн — LOW (производительность)

**Утверждение.** n-й фигура получается вызовом `Random(seed)` с n+1 итерациями
`randrange` (E:68–74). Спавн №n стоит O(n) → игра из N фигур стоит O(N²) и
пересоздаёт объект RNG на каждый спавн. Корректность (детерминизм, сериализуе-
мость) не нарушена — это цена выбранной схемы «seed+rng_calls в State».
Тесты пропускают: они проверяют детерминизм, а не стоимость.

## Проверено и держится

- **П-1. Сквозной цветовой шов движок→CLI→рендерер (направление 1).** Зонд 1:
  7 seed'ов × {6×4, 10×20, 5×6} × 40 шагов (команды CLI-глию `cli._apply` +
  `tick`), 1496 клеток активных фигур + все запертые клетки каждого кадра, RGB
  разобран регулярным выражением: цвет каждой клетки активной фигуры ==
  `PIECE_COLORS[piece_id]`; цвет запертых клеток после lock ==
  `PIECE_COLORS[piece_id]` (тот же id); количество строк кадра == height/2+2.
  **FAILURES: 0.** Дополнительно end-to-end subprocess
  (`python -m src.tetris_cli --seed 42 --ticks 6` с командами): 7 кадров × 4
  строки, финальный кадр **побайтово идентичен** in-process реплеи той же
  последовательности. Дефекта в шве нет.
- **П-2. Движок не мутирует входное состояние.** Зонд 2(a): deepcopy-сравнение
  state до/после каждой публичной функции (`try_move`, `try_rotate`, `soft_drop`,
  `hard_drop`, `tick`), включая lock-пути с вложенными списками: input
  deep-unchanged = True во всех 8 случаях. (Оговорка: это свойство движка, а не
  защита состояния от внешней мутации — см. A-3.)
- **П-3. Детерминизм.** Повтор команд даёт побайтово идентичный вывод (зонд 1);
  последовательности фигур по seed воспроизводимы (существующие тесты + зонды).
- **П-4. Wall-kick у обеих стен одновременно.** Вертикальный I на width-3 доске:
  `try_rotate(+1)` и `(-1)` → None (все 5 kick-смещений коллизируют). Корректно.
- **П-5. Выбор kick детерминирован порядком `KICKS`.** При свободных и +1, и −1
  выбран +1 (x=5 из x=4) — прямое следствие закреплённого кортежа; поведение
  согласовано с документом, но не защищено тестом (пробел 4 в таблице).
- **П-6. Game over внутри hard_drop наступает** (lock→spawn коллизия →
  `game_over=True`, lines_cleared=0) — поведение верное; тестовый пробел (2).
- **П-7. Zero-distance hard_drop** (фигура уже стоит): lock происходит на месте,
  спавн следующей — корректно.
- **П-8. No-op после game over** для всех операций (существующие тесты
  T-engine:244 подтверждены, повторных нарушений зондами не найдено).
- **П-9. Завершение по q и SIGINT.** `q` в pipe → rc 0 (и в bounded, и в
  интерактивном режиме); SIGINT → rc 0 (существующие тесты + зонд 3b).
- **П-10. Bounded-режим:** пустой/DEVNULL stdin допустим, ESC[H не emitted,
  идентичные запуски побайтово идентичны, `q` останавливает до тиков
  (существующие T-cli 3–6 подтверждены; повторных нарушений зондами нет).
- **П-11. ESC[H-гейт:** HOME только после первого кадра и только при TTY-stdout;
  pipe-поток побайтово равен TTY-потоку без HOME (существующие T-cli 8–9).
- **П-12. Рендерер не импортирует движок** (существующий тест T-render:160;
  зонды подтверждали отсутствие `tetris_engine` в `sys.modules` при импорте CLI-гли).

## Приоритет находок

**Критично для следующей игры/тикета:**
1. **A-1 + A-2 (+A-3 как корень)** — состояние не является независимым снимком:
   алиасинг строк после очистки и разделение board между состояниями. Любой
   тикет про историю/реплей/снапшоты/откаты или про сериализацию State упрётся в
   это первым. Это единственная находка, которая *уже сейчас* воспроизводится на
   состоянии из собственного теста (4-рядный клир).
2. **A-4** — контракт EOF требует решения до того, как интерактивный режим начнут
   использовать в скриптах/обёртках (сейчас это бесконечный процесс).
3. **A-5** — единственный шов, где «правильный код, неправильные цвета» прошёл бы
   незамеченным; защитный тест — самая дешёвая страховка.

**Важно, но не блокирует:** таблица пробелов тестов (особенно 1–2: они же
скрывают A-1), A-6.

**Косметика:** A-7, A-8, A-9, A-10.
