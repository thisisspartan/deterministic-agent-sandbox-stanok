# fire3d — объёмный 3D-огонь в консоли (ticket 041)

Консольная программа: 3D-пламя в воксельной сетке W×H×D, ASCII-рендер на
тёмном фоне, вращение сцены стрелками ←/→ вокруг вертикальной оси (y).

## Запуск

```bash
node src/fire3d/main.js
```

- **TTY** (интерактивно): raw mode, альтернативный экран, скрытый курсор,
  цикл 30 FPS. Пламя живёт бесконечно до выхода.
- **Non-TTY**: рендерятся фиксированные 10 кадров (с `step()` между
  кадрами) в stdout, затем `process.exit(0)` — без терминала не вешается.

## Управление

| Клавиша | Действие |
|---|---|
| `←` (normal: CSI `\u001b[D`; application: SS3 `\u001bOD`) | вращение против часовой: `angle -= ROT_STEP` |
| `→` (normal: CSI `\u001b[C`; application: SS3 `\u001bOC`) | вращение по часовой: `angle += ROT_STEP` |
| `↑` / `↓` (CSI `\u001b[A/B`, SS3 `\u001bOA/B`) | игнор |
| `q` / `Q` / `ESC` / `Ctrl+C` | выход (восстановление терминала всегда) |

`ROT_STEP = π/36 ≈ 5°`. Стрелки работают в **обоих** cursor-key режимах
терминала (ticket 045): normal — CSI `\u001b[C` / `\u001b[D`, и application
cursor key mode (DECCKM on) — SS3 `\u001bOC` / `\u001bOD`. Удержание стрелки
даёт автоповтор соответствующих последовательностей терминалом → плавное
непрерывное вращение. Прочие последовательности (F-клавиши, `↑`/`↓`,
`ESC O x`, paste и т. п.) игнорируются. Одиночный `ESC` (буфер из одного
байта `0x1b`) — выход; `ESC O …` — НЕ одиночный `ESC`.

## Диагностика (ticket 045)

**Баннер возможностей.** При запуске в TTY — **до** входа в альтернативный
экран (до `ui.attach`) — app пишет в **stderr** одну строку:

```
fire3d: <W>x<H> rows=<R> cols=<C> color256=<yes|no>
```

- `<W>x<H>` — размеры сетки (дефолт 48×24);
- `<R>` / `<C>` — `process.stdout.rows` / `process.stdout.columns`;
  `?`, если undefined;
- `color256` — результат детекта (`COLORTERM=truecolor` или `TERM` содержит
  `256color`).

Для `--frame` и non-TTY `renderStatic` баннер **не** пишется. Строка
позволяет диагностировать «чёрный экран» до появления кадра: `rows=?` /
`cols=?` — терминал не сообщает геометрию, `color256=no` — работает
16-цветный фолбэк.

**Самодиагностика `--frame`.** `node src/fire3d/main.js --frame` отрисовывает
один кадр разгоревшегося пламени и `exit(0)` — позволяет проверить вывод в
своём терминале без интерактивного режима (подробно — в разделе
«Флаг `--frame` (self-test)»).

## Выход и ошибки старта (ticket 045)

**Чистый выход.** `stop()` перед восстановлением курсора и выходом из
альтернативного экрана всегда очищает область кадра: `CURSOR_HOME
(\u001b[H)` + `rows_screen` строк по `cols` пробелов (тот же расчёт, что в
`render()`: `cols = min(W, floor(columns))`, `rows_screen = min(H,
max(2, rows-1))`, без `rows` — `H`) + `'\n'` + хвост-очистка `ESC[J]` — без
завершающего `'\n'`, если кадр доходит до последней строки экрана
(`rows_screen == rows-1`), как в компактном кадре. На терминалах **без**
alt-screen поддержки на основном экране не остаётся последний кадр.

**Ошибки старта.** Тело `start()` обернуто в try/catch: при ошибке
(например, MODULE_NOT_FOUND) — best-effort восстановление терминала
(`setRawMode(false)`, `CURSOR_SHOW + ALT_OFF`), одна строка
`fire3d: <message>` в stderr и `exit(1)` — без сырого стектрейса.

## Параметры

- `opts.W`, `opts.H`, `opts.D` — размеры сетки (дефолт **48×24×48**);
- `opts.seed` — seed PRNG (дефолт **1337**); `opts.rng` — инжектируемый PRNG
  (дефолт `mulberry32(seed)`);
- `opts.decay` — затухание тепла по высоте, clamp [0.85..0.92] (дефолт 0.88);
- `opts.fpsMs` (в `attach`) — период кадра (дефолт 33 мс ≈ 30 FPS).

## Как читать глифы плотности

Каждая экранная ячейка — воксель с максимум heat после проекции. Тепло
маппится на набор глифов `FLAME_GLYPHS = ' .,;:~*oO@'` — от редкого к
плотному:

```
 ' '  — пусто / тёмный фон (heat ≤ 0.08), цвет 234
 , ;  — слабые, разреженные языки
 : ~  — средняя плотность
 * o  — плотное пламя
 O @  — горячее ядро (heat → 1)
```

Кирпичей/рамы (▓ █ ▒) нет — пламя горит на всю сетку.

## Палитра (render) — ticket 042

Тепло ячейки → 256-цветные коды `\x1b[38;5;Nm` по `colorIndex` (те же
ступени, что в 2D-модуле `src/fire/fire.js`): `heat ≤ 0` → тёмный фон
(234); затем тлеющий тёмно-красный край (160) → красный (196) → оранжевый
(202/214) → жёлтый (226) → горячее ядро белый (231). Линейная интерполяция
между ступенями; hotter ячейка → индекс цвета не меньше, чем у холоднее.
Глиф плотности (`FLAME_GLYPHS`) по-прежнему зависит только от плотности
тепла. Соседние ячейки одного цвета объединяются в один run — один
escape-код на run (кадры короче). Чистые терминалы (без цветов) видят
ASCII-форму пламени, терминал с цветами — цветное пламя.

## Устойчивость к «чужим» терминалам (ticket 044)

### Адаптация кадра к высоте терминала

`render(state, width, angle, opts)` принимает новый 4-й аргумент `opts`
(может быть `undefined`): `opts.rows` — число строк терминала.

- `rows_screen = min(H, max(2, rows - 1))`; `rows` не задан/не число →
  `rows_screen = H` (старое поведение).
- Рисуются **нижние** `rows_screen` строк: y от `rows_screen - 1` до 0
  (база пламени y=0 всегда видна, верхушка отрезается).
- Если `rows_screen == rows - 1` (кадр доходит до последней строки экрана),
  кадр = `CURSOR_HOME + строки.join('\n')` — **без** завершающего `'\n'` и
  **без** `\x1b[J]`: иначе `'\n'` упирается в нижнюю границу и скроллит
  экран каждый кадр (30 FPS) — «бегущая» чёрная картинка. Последний ранг
  полностью покрыт поячеечными глифами, скролл невозможен.
- Иначе (кадр короче экрана) — обычный формат
  `CURSOR_HOME + строки.join('\n') + '\n' + \x1b[J]`.
- `width`/`cols` — без изменений (`min(W, floor(width))`).

### Фолбэк на 16 цветов

Чистая функция `colorCode(h, color256)` (экспортируется):

- `color256 === true` (дефолт) — текущее поведение: `\x1b[38;5;Nm`,
  `N = colorIndex(h)`, для `h <= 0` — тёмный фон 234.
- `color256 === false` — 16-цветные коды **без** интерполяции (ближайший
  стоп снизу), терминалы без 256-цветов не теряют картинку:

| heat | код | цвет |
|---|---|---|
| `h <= 0` | `\x1b[90m` | bright black (фон) |
| `0 < h < 0.3` | `\x1b[31m` | красный |
| `0.3 <= h < 0.5` | `\x1b[91m` | bright red |
| `0.5 <= h < 0.8` | `\x1b[33m` | жёлтый |
| `h >= 0.8` | `\x1b[97m` | белый |

`render` принимает `opts.color256` (дефолт `true`) и строит коды через
`colorCode`; мержинг однотонных прогонов и завершающий `\x1b[0m` — без
изменений.

### Определение возможностей (main.js)

```js
color256 = (COLORTERM || '').toLowerCase() === 'truecolor'
          || /256color/.test(TERM || '')
```

Значение передаётся в `ui.attach` (TTY) и в `renderStatic` (non-TTY);
`ui.js` пробрасывает `opts.rows` / `opts.color256` в `render`
(`rows`: `opts.rows` → иначе `io.rows` → иначе `process.stdout.rows`).

### Флаг `--frame` (self-test)

```bash
node src/fire3d/main.js --frame
```

Отрисовывает **один** кадр разгоревшегося пламени (после 30 вызовов
`step()`) в stdout и `exit(0)` — работает и в TTY, и в non-TTY, чтобы
пользователь мог проверить вывод в своём терминале.

## Структура кадра (ANSI)

Кадр `render()` — одна строка-блок (см. адаптацию к высоте выше):

```
CURSOR_HOME (\x1b[H) + строки.join('\n') + '\n' + хвост-очистка (\x1b[J])
```

Хвост-очистка — `\x1b[J` (стереть **от курсора до конца экрана**), НЕ `\x1b[2J`
(стереть **весь экран**). После последней строки идёт `'\n'`, поэтому курсор
оказывается НИЖЕ кадра, и `\x1b[J` счищает только хвост под кадром, а не сам
кадр. (Использование `\x1b[2J` стирало бы только что нарисованный кадр →
вечный чёрный экран; исправлено в ticket 043.)

## Индексация heat

Плоский `Float32Array` размера `W*H*D`, индекс `y*W*D + x*D + z`
(y: 0 = основание … H-1 = верх; x: 0..W-1; z: 0..D-1).

## Детерминизм

Один seed + одна последовательность `step()` ⇒ идентичные кадры
`render()` (PRNG инжектируется, дефолт `mulberry32(seed)`).
