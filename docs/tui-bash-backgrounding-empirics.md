## 3. Эмпирическая модель авто-фоновки Bash-вызова (Claude Code 2.1.88)

**Правило (подтверждено тестами):** Bash-вызов фонуется, когда команда НЕ умещается
в tool-timeout (дефолт 120с). `trz=15000` — это бюджет ПРОВЕРКИ (подождать до ~15с,
затем решить по остатку timeout), а НЕ авто-порог. Отсюда и «расхождение» источников:
15s и 120s — два разных механизма, которые складываются.

### 3.1 Прогоны (голые команды, без `bash -c`/`echo`)

| Команда (весь Bash-вызов) | tool-timeout | Результат |
|---|---|---|
| `sleep 10` | 120с (дефолт) | блок 10с → «completed» |
| `sleep 60` | 120с (дефолт) | блок 60с → «completed» |
| `sleep 90` | 120с (дефолт) | блок 90с → «completed» |
| `sleep 60` | 17с | **фон на ~15с**, уведомление, exit 0 |
| `sleep 60` | 45с | **фон на ~15с**, уведомление, exit 0 |

Признак фона в результате вызова: `Command running in background with ID: … Output
is being written to: …`. Завершение приходит отдельным уведомлением (exit code).

### 3.2 deny-list `_5Y=["sleep"]` — моё раннее чтение НЕ подтвердилось

Голый `sleep 60` как ВСЯ команда фонуется (строки 4–5 таблицы). deny-list либо не
применяется на этом пути, либо матчит не то, что я предполагал. Практически
«sleep блокирует TUI» происходит из-за большого tool-timeout, а не deny-list.

### 3.3 Почему `sleep 10` — НЕ дискриминирующий тест

`sleep 10` завершается на 10с, что меньше ЛЮБОГО порога (15с и 120с) — при любом
пороге результат одинаковый («completed»). Для различения нужна команда в интервале
(15с, 120с): `sleep 60`/`sleep 90`.

## 4. Выживание после рестарта TUI (механизм `--background`)

Проверено на POSIX-уровне. Механизм `--background` — `subprocess.Popen(..., start_new_session=True)`
в `cmd_dispatch_run`, что эквивалентно `setsid()`. Воспроизведение:

```bash
$ setsid -f sh -c 'echo $$ > /tmp/stanok-setsid-test.pid; exec sleep 45' >/dev/null 2>&1; echo $?
0
$ ps -o pid,ppid,sid,pgid,stat,cmd -p $(cat /tmp/stanok-setsid-test.pid)
    PID    PPID     SID    PGID STAT CMD
  76288       1   76288   76288 Ss   sleep 45
# из НОВОГО шелла (аналог переоткрытого TUI), после смерти родителя:
$ ps -p 76288   # ALIVE: PPID=1, SID=PGID=pid, Ss (своя сессия, нет управляющего терминала)
```

Вывод: setsid-детaч переживает смерть родителя (PPID → 1, новая сессия/группа, нет
управляющего терминала → нет SIGHUP; другой pgid → не попадает в group-kill).
Для супервайзера: «закрыл TUI → прогон продолжился → `status`/`stop` работают».

## 5. Практические следствия для супервайзера

1. `launch.sh <ticket> <label> --background` возвращается мгновенно (суб-секунда) —
   **никогда не фонится**, TUI не блокируется. Канонический режим (§3).
2. НЕ-background прогон (реальный 20–40 мин) фонуется при любом пороге — TUI не
   блокируется, но результат придёт уведомлением.
3. Долгий Bash-вызов в TUI с дефолтным 120с таймаутом БЛОКИРУЕТ до ~120с. Если нужно
   фоновое выполнение без блокировки — явный `run_in_background` или малый tool-timeout.
4. Полное отключение авто-фона: `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`.
5. Порог 40 мин в §3 (зависший прогон) НЕ связан с авто-фоновкой — это про
   `elapsed_s` реального прогона; остаётся в силе.
